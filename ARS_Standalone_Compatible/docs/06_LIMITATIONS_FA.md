# محدودیت‌های لازم برای تصمیم استقرار

**UDP و TCP دو Transport مستقل با دستورات یکسان هستند، نه تضمین‌های تحویل یکسان.** UDP نه اتصال واقعی TCP دارد و نه تضمین ترتیب و تحویل. پیاده‌سازی حاضر از retry request با همان requestId، dedup در RAM سرور (IP:port+requestId تا ۱۲۰ ثانیه)، ACK live event، heartbeat و fragment/reassembly استفاده می‌کند. اما این‌ها دقیقاً تضمین persistent Exactly-once نمی‌سازند. اگر سرور بعد از ذخیره restart شود و ACK اولیه گم شده باشد، درخواست دوباره می‌تواند رکورد تکراری درج کند. رویداد زنده هم پس از تمام‌شدن retryها می‌تواند از دست برود. برای داده‌های حیاتی، durable ingestion idempotency (در Redis/SQL با کلید یکتای درخواست) و replay آگاهانه client لازم است.

هر دو پروتکل در حالت فعلی توکن را به‌صورت plaintext روی شبکه حمل می‌کنند. **برای اینترنت مناسب نیستند**؛ از LAN قابل اعتماد، VPN، ACL و firewall بهره بگیرید. برای Production، احراز هویت با نقش‌های مجزا، rotation توکن، TLS/DTLS یا secure tunnel و limit per IP اضافه شود. UDP حداکثر ۱۲۸ peer و ۶۴ subscription/peer دارد. نتایج در RAM cache می‌شوند و در بار خیلی بالا ممکن است محدودیت ۲۰۴۸ درخواست cache یا Event Live برسد.

UDP fragmentation در سطح برنامه برای پاسخ‌های بزرگ وجود دارد ولی در محیط واقعی آزمایش نشده؛ بسته‌های بزرگ را به صفحه‌های کوچک محدود کنید. `history` و `recent` با paging پشتیبانی می‌شوند. جست‌وجوی Redis به صورت scan محدود و best effort است. `HotColdStore` همچنان دارای عملیات blocking است؛ برای تأخیر کم و نرخ بسیار بالا به تست P99 و بهینه‌سازی نیاز دارد. هیچ یک از این محدودیت‌ها به معنای حذف قابلیت‌ها نیست؛ بیان شفاف سطح تضمین فعلی آن‌هاست.
